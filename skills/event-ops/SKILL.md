# event-ops：把一场活动变成下一场更好的活动

这个技能做三件事，按顺序循环：

```
跑单（开场前） → 复盘（散场后） → 迭代（变成下一场的跑单） → 跑单 → …
                      ↓
              已关闭的决策（不再重开）
```

**它不是活动策划模板。** 策划模板告诉你「活动应该有哪些环节」；这套东西假设你
已经办过至少一场，要解决的是**为什么那一场没达到预期，以及下一场改什么**。

用户说「帮我出跑单」「复盘一下」「下一场怎么改」，或者贴一段活动当天的记录过来，
就进对应的阶段。**没办过任何一场就来问的，先说清楚：第一场怎么排都行，这套东西
的价值从第二场才开始。**

---

## 〇、先建两份文件（第一次用这个技能时）

| 文件 | 放什么 | 谁看 |
|---|---|---|
| `跑单-YYYY-MM-DD.md` | 这一场当天照着做的东西 | 主办人和帮忙的人 |
| `复盘-YYYY-MM-DD.md` | 这一场发生了什么、为什么、下一场改什么 | 主办人 |
| **`已关闭的决策.md`** | **定了就不再重开的事，一行一条，带日期和依据** | 主办人 + 任何来提建议的 AI |

**第三份是最容易被跳过、也最值钱的一份。** 理由见 §三。

模板在 `templates/` 下，直接抄。

---

## 一、跑单（开场前）

### 1.1 跑单不是流程表，是「当天不用再做决定」的清单

一份好跑单的判据只有一个：**把它交给一个没办过这个活动的人，他能照着跑下来。**

写完之后自问：**收到它的人会回「就这些？」还是「太难了」？** 前者说明交接成立，
后者说明还不够细。

### 1.2 必须写进去的六样

1. **真实的时间线**，不是理想的。用**上一场实际到场曲线**排，不要用公告时间排
   （见 §2.4，这是最常见的一个错）
2. **每个环节的硬约束**（时长、人数上限、有没有问答），以及**超了怎么办的一句话**
3. **主办人当天要做的动作**，越少越好。能摊给参与者的就摊出去（见 §4.3）
4. **明确写出「不用做的事」**。这一段比「要做什么」更能降低接手人的压力——
   没写的事他会自己脑补出来
5. **三到五种可能出问题的情况**，各给一句话的处理（冷场、人太少、有人打断、下雨）
6. **散场后要记的数字**，就地列好。当场不记，两小时后全忘

### 1.3 需要人照着念的话，给原文

不要写「主持人宣布开始」，要写出那一句：

> 「人差不多了我们开始吧，第一次来的朋友做个 45 秒自我介绍，来过的就不用了。」

**要不要自己组织语言，是接手这件事最大的心理成本。**

## 二、复盘（散场后）

### 2.1 ★ 先分开：观察 / 推断 / 猜测

**这是整套方法里唯一不能省的一步。**

拿到一个现象，先用一句话写出「**这个观察单独能证明什么**」，再给解释。

| | 例 |
|---|---|
| ❌ 观察当解释 | 「大家不爱发言」——这解释不了任何事，只是把现象重述了一遍 |
| ✅ 观察 | 「90 分钟里只有 3 个人说过话」 |
| ✅ 推断 | 「发言成本太高」——**如果我错了，最可能错在哪：也许是话题本身没人关心** |
| ✅ 待验证 | 「n=1，下一场再看」 |

**结论分级标注**：实测（有记录）/ 推断（从实测推出）/ 猜测（没有直接依据）。
**每个「推断」后面跟一句「如果我错了，最可能错在哪」**——写不出来说明还没想清楚。

### 2.2 ★ 找设计矛盾，不要找执行失误

复盘最容易停在「下次记得计时」这种地方。**那不是根因，那是症状。**

问一次：**这件事是没做到，还是这个设计本来就做不到？**

真实例子：某场活动「自我介绍超时」，第一反应是「忘了计时」。
往下问一层——活动被定调成「随便聊」，同时又排了「自我介绍轮 + 逐个展示」的
结构化议程。**在人陆续到场的格式里跑结构化议程，必然失控。**
根因不是没计时，是这两件事不能同时要。

**判据**：如果你的改进措施是「下次注意」「记得提醒」「加强管理」，那你还停在症状层。

### 2.3 ★ 规模会改变性质，不只是改变数量

同样一件事，人数变了就不是同一件事：

> 30 个人做**宣讲**没问题。30 个人做**轻松聊天**就出问题——因为任何一个人开口，
> 都要占用另外 29 个人的时间，于是大部分人选择等，等到散场后三五个人的小圈子。

所以「人多了不好办」这个说法要拆成：**是规模的问题，还是规模与形式不匹配的问题？**
后者的解法是换形式或换单元大小，不是控人数。

### 2.4 至少量这几个数

| 数 | 为什么 |
|---|---|
| **实到人数** | 报名数不是到场数。到场率是所有规划的基数 |
| **到场曲线**（每半小时到了多少） | 决定真正的开始时间。**大多数活动的议程都比实际可用时间长** |
| **回头率**（第几次来的举手，3 秒） | 稳定的到场数可能是漏桶：每场靠新人撑、老人不回来。**这个数比总人数更能说明健康度** |
| **散场后自发停留多久** | 见 §2.5 |
| 每个环节实际用了多久 vs 计划 | 差值最大的那个就是下一场要改的 |

⚠️ **不要用报名系统的数据冒充到场数据。** 库里知道谁报了名，不知道谁真的来了。
回头率只能现场问。

### 2.5 ★ 留意「价值发生在议程之外」

如果连续两场，最有价值的交流都发生在正式流程结束之后（散场后的走廊、饭桌、
群里），那不是巧合，是信号：

> **正式议程没有在产出价值，它在产出「知道该去找谁」。**

一旦确认，议程的目标要换：**它是索引，不是内容。** 索引的评价标准是快、准、
可检索，不是完整。而且**议程之外那一段应该被正式写进议程**——它已经是最值钱的
时段了，只是没被承认。

### 2.6 复盘要不要给参与者看

**分开两件事**：

- **对内**（已经来过的人）：复盘是信任资产。「我发现问题了，所以我改了」
- **对外**（没来过的人）：复盘是自曝。他第一次听说这件事就先听到毛病

**能对外用的只有一句话**，而且必须紧跟反转：「上一场有个明显的问题，所以这一场
我把流程重做了。」重点落在「我改了」，不在「有问题」。

★ **但对内那一份值得认真发。** 实测：把「问题 + 我的改法 + 哪里还没想清楚」
发给参与者，换回来的是设计建议而不是「辛苦了」——**一条消息的成本，换回来的是
屋子里所有人的设计能力**。做对两件事就行：①先说问题再说改法，把接缝亮出来，
别人才有地方插话 ②结尾的提问要是真提问。

## 三、已关闭的决策（这一份不要跳过）

### 3.1 它解决什么

反复举办的活动，同一个提议会反复出现：要不要收费、要不要租设备、要不要换场地、
要不要开分场。每次都从头讨论一遍，而且**新来的人（包括新来的 AI）不知道这事去年
已经吵过了**。

一张表就够：

| 日期 | 决定 | 依据 |
|---|---|---|
| 2026-08-09 | 永远免费，不收门票 | 向 20 人小额收费的天花板 ≈ 一两单 B2B，却要付出全部社群代价 |

**依据比决定更重要。** 只写决定，下次有人问「为什么」还是要重来一遍。

### 3.2 什么时候往里加

定了一件**不希望三个月后再讨论一遍**的事，当场加一行。不确定的不要加——
这张表的权威性来自它只装真正定死的东西。

### 3.3 什么时候可以重开

**有新证据的时候，而且要说清楚新在哪。** 「我改主意了」不算新证据；
「原来的依据是 n=1，现在有三场数据了」算。

重开时**把旧行划掉但保留**，写清楚为什么推翻。删掉它等于让下一个人重走一遍。

## 四、迭代：把复盘变成下一场的跑单

### 4.1 一次只改一个变量

同时换格式和换场地，下一场的好坏就归不了因。**排个序，一场改一件。**

例外：几件事互相依赖时一起改（比如「取消自我介绍」和「加开场索引环节」）。

### 4.2 改法要能被执行，不能是态度

| ❌ | ✅ |
|---|---|
| 下次注意控制时间 | 每人 5 分钟，讲完就下，**当场提问一律说「等下去他那桌聊」** |
| 让大家多交流 | 明说一条规矩：**走开不用打招呼，也不用说再见** |
| 提高参与感 | 每个人的分享**固定以一句「我现在需要什么」收尾** |

### 4.3 ★ 主办人的活能摊出去就摊出去

反复办的活动最大的风险是**只有一个人能办**。他病了、出差了、搬走了，活动就停了。

做法不是「找个人代班」，是**把只有主办人能做的事减到零**：

- 列出主办人当天做的每一件事，逐条问「这件事非他不可吗」
- 能摊给参与者的摊出去。**上台分享的人本来就要开口，开场和收尾那两句话给他们**
- 需要预付钱的环节想办法取消掉——**「有人得先掏钱」是最难交接的一种依赖**
- 剩下的写成跑单（§一），交给任何一个来过两次的人

**顺手的测试**：主办人在场但不主持一次，坐在角落当参与者。出问题随时能接，
而这把「能不能交出去」从一个赌注变成一个可测的问题。

### 4.4 几条从实践里长出来的判断

这些不是通则，是别人踩出来的，拿去当起点：

- **内向的人要的不是「更容易开口」，是「不开口也不尴尬」。** 破冰环节常常做反了方向——
  强制配对没有退出通道，比不做更糟。给一个可以只听不说、随时能走的位置
- **降低门槛 ≠ 取消这件事的必要性。** 后者几乎总是更好，只是更难想到
- **不要试图让所有人互相认识。** 三十个人轮一圈自我介绍要半小时，而听完没有人
  记得住三十个人——**花掉三分之一的时间，产出接近零**。目标是让每个人碰上
  三五个对的人
- **时间雷打不动。** 一旦「这周有没有」变成一个需要问的问题，这个活动就开始死了
- **收集必须当场兑现回报。** 收了大家的问题却没人看到结果，第二次就没人填了

## 五、绝对不做

- **不编数字。** 没记到就写「没记」，不要估一个填上去
- **不把单次观察写成结论。** n=1 就标 n=1
- **不在复盘里给「加强沟通」这类没有动作的改进**
- **不把已关闭的决策当成可以随便重开的建议**——先读那张表，再提方案
- **不替主办人决定要不要长大**。规模上限是他的判断，这个技能只负责把代价说清楚

## 六、这套东西是从哪来的

来自悉尼一个每周四上午的 AI 聚会（[vibethursday.com](https://vibethursday.com)）
从第一场到第三场的真实迭代：一场 30 人的活动，90 分钟只聊透 3 个产品、
大部分人没说上话，最后靠换掉「最小讨论单元」而不是靠加强管理解决。

上面每一条判断都有出处，不是通用建议。**但它们是起点不是答案**——
你的活动是什么形状，只有你的数据知道。
